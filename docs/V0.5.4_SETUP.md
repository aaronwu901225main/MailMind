# MailMind v0.5.4：Schema-driven Email Event Extraction Core

**基礎版本：** 已在你的 HPC 驗收的 v0.5.3（LINE Agent + 7 個 MCP Tools）。本壓縮檔是**增量更新包**，不能當成完整專案使用。它**不覆寫**既有 `app/routes/ingest.py`、LINE 路由、Agent Worker、Flask 電費 Bot 代理、`.env`、SQLite DB，或過去的 Knowledge Chunks/Embeddings。

## 0. 新增什麼？

| 內容 | 說明 |
| --- | --- |
| Schema Registry | `transaction`, `deadline` 兩類；Pydantic 驗證與版本管理，未來可擴增 `order`, `bill`, `appointment` |
| Local Extractor | 從 `knowledge_chunks` 的 `body` / `attachment` 做保守 Regex 擷取；完全離線 |
| 可選 Gemini Fallback | `--mode hybrid --allow-cloud` 加額外 `.env` 同意，才會傳送遮罩後的節錄，不會被 Gmail 收信流程自動觸發 |
| Source Validation | 交易金額、幣別、日期必須能在原始來源片段中查證；無法確認的資料為 `review`，不參與統計 |
| SQLite | `structured_events`, `event_extraction_runs`；同一封可包含多事件，保存來源 Chunk ID、擷取方式及狀態 |
| MCP +4 | `search_events`, `aggregate_events`, `get_event_detail`, `get_extraction_coverage`（固定 Account ID 的唯讀工具） |
| CLI | `extract_events`, `query_events`, `check_events` |
| Health | `/health` 使用 `app.version`，避免以往硬編碼版本號忘了改 |

**特別注意：** 本版沒有讓 LINE Agent 自動路由到這 4 個統計工具。v0.5.3 的 LINE 問答保持原狀；CLI、MCP Client 可先驗收統計。**只靠目前的信用卡消費通知，也無法證明銀行的真實總花費**。計算結果只代表「已收到、已建立內文索引、已成功擷取、已驗證」的事件。

## 1. 安裝、備份、測試

先在 `MailMind` tmux 停止 Uvicorn；停止或暫停正在寫入同一份 SQLite 的相關 Worker，備份後再恢復。操作目錄：

```bash
cd ~/MailMind
source .venv/bin/activate
cp -a app app.backup.before-v054
cp -a scripts scripts.backup.before-v054
python - <<'PY'
import sqlite3
from pathlib import Path
s = Path('data/mailmind.db')
t = Path('data/mailmind.db.before-v054')
with sqlite3.connect(s) as src, sqlite3.connect(t) as dst:
    src.backup(dst)
print('✅ SQLite 備份完成')
PY
```

上傳 `MailMind-v0.5.4-Events-patch.zip` 後：

```bash
unzip -o MailMind-v0.5.4-Events-patch.zip -d .
python -m compileall -q app scripts
pytest -q
python -m scripts.check_setup
python -m scripts.check_events
```

預期會多出 `structured_events` 與 `event_extraction_runs`。由 `Base.metadata.create_all()` 新建空表，既有信件不會被刪除。**本地隔離測試 17 passed；你的 HPC 完整測試仍需以以上命令為準。**

重新啟動 Uvicorn，確認：

```bash
curl -s http://127.0.0.1:8000/health
# 預期 version: 0.5.4
```

## 2. 先用本地 Regex 擷取 20 封

這一步**不會呼叫 Gemini、不需要載入 E5、也不會發 LINE**：

```bash
python -m scripts.extract_events \
  --account-id '你的ACCOUNT_ID' \
  --max-emails 20 \
  --mode local
```

同一封信的相同來源版本會跳過，重跑可接續下一批。舊郵件如果沒有 `body` 或 `attachment` 原文，會記為 `no_source`，**不會嘗試從 Gemini 摘要推算金融金額**。新郵件如果 `knowledge_chunks` 尚未建立，先確認 v0.5.1 的索引機制。來源變更時，同封郵件舊事件會在同一個 SQLite 交易中被替換，避免舊金額與新金額同時納入加總。

查詢擷取覆蓋情況：

```bash
python -m scripts.query_events \
  --account-id '你的ACCOUNT_ID' \
  --action coverage
```

查看交易與待審核資料：

```bash
python -m scripts.query_events \
  --account-id '你的ACCOUNT_ID' \
  --action search --event-type transaction --include-review
```

## 3. 查看交易金額的「保守合計」

**以下日期只作示例，請改為你要驗證的期間。** 左閉右開（包括 11/23，不包括 11/30）。日期以擷取到的交易原文日期為準，不是郵件抵達日。

```bash
python -m scripts.query_events \
  --account-id '你的ACCOUNT_ID' \
  --action aggregate \
  --event-type transaction \
  --start-date 2026-11-23 \
  --end-date 2026-11-30 \
  --status purchase
```

輸出使用 `amount_minor` 整數分（TWD 100 元 = 10000 分）；各幣別分開加總，未進行匯率換算。`purchase` 不含 `refund`、`reversal`、`authorization`；若要看退款須另行查詢 `--status refund`。不同狀態不會被當成一筆交易的唯一生命週期，因為許多銀行不提供可靠交易 ID。不可將這個合計當作真正帳單或財務憑證。

查看已確認截止事項：

```bash
python -m scripts.query_events \
  --account-id '你的ACCOUNT_ID' \
  --action search --event-type deadline \
  --start-date 2026-11-23 --end-date 2026-12-01
```

## 4. 可選 Gemini Fallback（敏感郵件請先不要啟用）

`local` 的規則偏向高精確、低召回，遇到不同版型可能漏掉事件。`hybrid` 可以對沒有本地 verified 事件的片段使用 Gemini 做候選擷取，但**模型產生的欄位仍須通過來源驗證**。不可靠的結果不得進入 verified 加總。這個模式預設完全關閉。

只有你明確同意把少量郵件原文節錄送至 Gemini 才在 `.env` 加：

```ini
MAILMIND_EVENTS_ALLOW_CLOUD=true
```

並且執行時還要雙重確認：

```bash
python -m scripts.extract_events \
  --account-id '你的ACCOUNT_ID' \
  --mode hybrid --allow-cloud --max-emails 3
```

最多 5 封 Email / 執行；每封至多 6 個 Chunk、每個 900 字元供模型使用。雖有基本 Email／手機／Token／敏感連結遮罩，**不是可靠 DLP 去識別系統**，不建議把真正的銀行通知交給免費層 Gemini 做測試。可先使用自製的虛構通知。若要完全離線，不設定此開關、只執行 `--mode local` 即可。

`hybrid` 不是「每封都送雲端」，也不是任意信都能提取出事件；日期年份不明、金額或證據不完整時仍應漏掉或進入 review，而不是猜測。

## 5. MCP Tool 驗收（7 → 11）

原本的 7 個 Tools 不變，新增 4 個帳號限定工具：

- `search_events(event_type='transaction',start_date='',end_date='',limit=20)`
- `aggregate_events(event_type,start_date,end_date,status='purchase')`
- `get_event_detail(event_id)`
- `get_extraction_coverage()`

可以沿用你原先的 MCP Client 測試流程：`client.list_tools()` 應顯示 11 個 Tool。**MCP Server 是本機 stdio 程序，不要公開到 ngrok/Flask**；帳號範圍仍綁定 `MAILMIND_MCP_ACCOUNT_ID`，不讓 LLM 自行帶 `account_id`。

測試 `aggregate_events` 時使用 `start_date='2026-11-23',end_date='2026-11-30',event_type='transaction'`。沒有交易時回傳空陣列是正常的，不可用假資料冒充實測。

## 6. 擴充事件類型的方式

1. 在 `app/services/event_schema.py` 新增 Pydantic Schema（例如 `OrderEvent`），加入 `EVENT_SCHEMAS`。
2. 在 `event_extraction.py` 或新增專用 `extractor` 模組把來源郵件映射成該 Schema。
3. 在 `event_store.py` 中保持來源 ID、驗證狀態及 Event Fingerprint，確保不跨帳號或重複匯入。
4. 新增自己的測試郵件 Fixtures，驗證欄位精確率、時間與金額一致性。**新增事件類型後應調高 `EXTRACTOR_VERSION`，再批次重新擷取。**
5. 如需新的統計欄位，在 analytics 層用白名單查詢擴充，不提供任意 SQL MCP Tool。

## 7. 已知限制與回復方式

- 這是**抽取與結構化分析核心**，尚未將 Agent 的「我這週刷卡多少」自動導向 `aggregate_events`。下一階段是 Tool Routing 與失敗時的詢問／拒答邏輯。
- 日期只接受明確完整西元日期（`YYYY/MM/DD`, `YYYY-MM-DD`, `YYYY年MM月DD日`），沒有年份、民國年份、只寫星期幾的日期需擴充專用解析規則。截止事項僅以日期為主，尚未保存時間／時區。
- Chunk 有文字重疊，已提供邊界重複過濾；極端跨多 Chunk 的表格、PDF 影像未啟用 OCR 時仍可能漏掉。
- 信用卡授權通知、請款完成、退款與取消可能指向同一交易；本版按郵件事件記錄，**尚未支援跨封信的金融交易實體對帳與去重**。請勿用於正式財務決策。
- `review` 尚未實作 UI 人工確認流程，僅供 CLI 查看；未完成審核前不計入統計。
- 沒收到的郵件無法被統計，也無法由本系統驗證銀行已寄出的所有通知。
- 不會上傳整個附件檔案；會使用既有 Knowledge Chunk 文字。舊信缺原文仍須另行授權 Gmail 回填。
- v0.5.4 不需要新的 Python 依賴（使用既有 SQLAlchemy、Pydantic、可選 Google GenAI SDK）。
- 如需回復，停止 Uvicorn，恢復備份的 `app/`、`scripts/`。新增 SQLite 兩表可以保留；**不要把舊的 DB 備份直接蓋回已有新郵件的 DB**。

## 8. 實際建議驗收

1. `pytest -q` 無回歸錯誤。
2. `check_events` 顯示新表。
3. 用兩三封**模擬信用卡通知**驗證金額、幣別、退款與截止日期。
4. `query_events --action aggregate` 手算驗證；確保輸出只有 verified，混合幣別分開顯示。
5. MCP 11 個 Tools 可呼叫、未授權帳號無法存取其他事件。
6. 現有 LINE `我的設定`、`查郵件 PDF 文字辨識失敗的原因` 仍正常。

**最重要：本次補上了結構化事件資料層，不代表 LINE 統計 Agent 已完成。**
