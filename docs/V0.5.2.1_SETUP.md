# MailMind v0.5.2.1：Retrieval Quality Improvement

> 適用於已完成 v0.5.2 的 MailMind。此版本**不會重新建立 Embedding**、不修改郵件去重機制，也不新增資料表。
>
> 目標：把「固定回傳前五個向量近鄰」改進成「先取候選、合併同封郵件，再選擇性判斷是否具有回答問題的直接證據」。

## 1. 功能

| 部分 | 行為 |
| --- | --- |
| 原 `hybrid_search` | 保留不變；原有 MCP 與 CLI 相容 |
| 查詢擴展 | 不需 LLM，以英數關鍵字、部分中文詞組做**有限**拆分，補充 FTS5 候選；非萬用同義詞引擎 |
| 來源合併 | 同一封信的 `body`、`summary`、`attachment` 會在結果中合成一封 Email，保留各自 `chunk_id` 與擷取文字 |
| 相關性判斷 | 透過 `--rerank` **明確選用**既有 Gemini API，將候選分成 `relevant`、`partial`、`irrelevant`；預設只回傳 `relevant` |
| 證據校驗 | 回傳的 Email ID 與支持它的 Chunk ID 必須出現在經帳號過濾的候選資料內，未知 ID 不予採納 |
| 免費策略 | CLI 預設不呼叫 Gemini；MCP 預設也不呼叫 Gemini；不增加背景 Worker、不使用新付費服務 |
| 無答案 | 不會為湊滿 `limit` 回傳無關的結果（**限啟用 rerank**）；沒有證據會回傳 0 筆 |

**重要差異：** 沒開 `--rerank` 時回傳的是 `relevance=unjudged`，只是「候選」，並未證實相關。E5 cosine（例如 0.85）不代表 85% 相關，RRF 也不是相關機率。Gemini 判斷仍有誤判可能，需要透過原始 Chunk 核對。

## 2. 安裝

建議先停掉 `MailMind` tmux 中的 Uvicorn；不用停止電費機器人、Cloudflare Tunnel、LINE Worker。確認專案位置為 `~/MailMind`。

```bash
cd ~/MailMind
source .venv/bin/activate

# 只備份本次會覆蓋的程式；此次不變更 SQLite schema
cp -a app app.backup.before-v0521
cp -a scripts scripts.backup.before-v0521

# 把下載的 ZIP 上傳到 ~/MailMind 後執行
unzip -o MailMind-v0.5.2.1-Relevance-patch.zip -d .

python -m compileall -q app scripts
pytest -q
python -m scripts.check_setup
```

**注意：** 新檔案 `tests/test_relevance_search.py` 是離線測試，不會真的呼叫 Gemini 或下載模型。若你額外有其他自訂程式碼，覆蓋前先 `diff`。

## 3. 先用本地模式測試（不花 Gemini API 額度）

此階段會讀 SQLite。如果加 `--semantic`，會載入已經下載的 E5 CPU 模型，請在 HPC 允許進行 CPU 推論的運算環境執行。

```bash
python -m scripts.search_relevant_emails \
  --account-id '你的ACCOUNT_ID' \
  --query 'PDF 文字辨識失敗' \
  --semantic
```

輸出將以 Email ID 分組，並標示 `relevance=unjudged`。這一步只驗證候選檢索、查詢拆解和郵件合併，不代表無關的信會自動消失。

## 4. 明確啟用 Gemini Rerank（可使用免費額度，但注意隱私）

**只有你明確加上 `--rerank`，才會把檢索到的候選郵件文字送給 Gemini。**

```bash
python -m scripts.search_relevant_emails \
  --account-id '你的ACCOUNT_ID' \
  --query 'PDF 文字辨識失敗' \
  --semantic \
  --rerank
```

預期的理想行為是只保留有足夠證據說明「掃描式 PDF 因缺少 OCR 無法擷取文字」的測試報告；但**尚未在你的真實 320 個 Chunks 上驗證此結果**。需要以實際輸出判定。若沒有符合條件的候選，允許回傳 0 封，並不是程式錯誤。

使用 `--include-partial` 可額外取得 `partial` 結果：

```bash
python -m scripts.search_relevant_emails \
  --account-id '你的ACCOUNT_ID' \
  --query 'PDF 文字辨識失敗' \
  --semantic --rerank --include-partial
```

**成本與隱私提醒：** 這裡呼叫的是現有 `GEMINI_MODEL` 與 `GEMINI_API_KEY`，通常為免費額度內使用，但會計入 API 使用量；免費層級可能有資料用於改善服務的條款。程式最多送出 10 封候選郵件、每封至多 2 個各 900 字元的證據片段，不上傳完整信箱或附件原檔。若郵件涉及機密資料，就只做本地查詢，不要加 `--rerank`。也不要在 CLI 中貼出私人郵件內容分享給他人。

Gemini API 出錯時 CLI 會清楚回報失敗，**不會假裝回傳的候選是已證實相關**；原本 Gmail 收信、摘要和 LINE 推播不受影響。因為沒有背景自動呼叫，本版暫不另外實作每天自動的 rerank 預算控管。

## 5. 新增第七個 MCP Tool

`search_relevant_emails(query: str, limit: int = 5)`

仍使用原本的 `MAILMIND_MCP_ACCOUNT_ID` 固定帳號範圍，不允許 LLM 傳入其他使用者的 Account ID。**不要把 MCP stdio 服務直接公開到 Cloudflare Tunnel**。

MCP 端預設完全不執行 Gemini / CPU embedding：

```ini
MAILMIND_ENABLE_SEMANTIC_QUERY=false
MAILMIND_ENABLE_GEMINI_RERANK=false
```

若在允許推論的運算節點執行，而且**明確同意將候選郵件內容傳送至 Gemini**，才可選擇啟用：

```ini
MAILMIND_ENABLE_SEMANTIC_QUERY=true
MAILMIND_ENABLE_GEMINI_RERANK=true
```

變更後需重新啟動 MCP 子程序；既有 Uvicorn 不會因這些設定自動發送郵件到 Gemini。請確保執行節點有 E5 模型快取。

### MCP 協定驗證

先確認 `.env` 有 `MAILMIND_MCP_ACCOUNT_ID`，之後：

```bash
python - <<'PY'
import asyncio, sys
from mcp import Client, StdioServerParameters

async def main():
    params = StdioServerParameters(command=sys.executable, args=['-m', 'app.mcp_server'])
    async with Client(params) as client:
        tools = await client.list_tools()
        print('Tools:', [tool.name for tool in tools.tools])
        result = await client.call_tool('search_relevant_emails', {
            'query': 'PDF 文字辨識失敗', 'limit': 5,
        })
        print('is_error:', result.is_error)
        for item in result.content:
            if item.type == 'text':
                print(item.text[:1600])
asyncio.run(main())
PY
```

尚未在本地開發容器執行 MCP SDK 端到端測試，請以你 HPC 的這段輸出驗收；本版已做後端工具函式的帳號隔離測試。

## 6. 驗收與已知限制

1. `pytest -q` 保留原有測試並通過新增測試。
2. 不加 `--rerank`：有 Email 分組、`unjudged`，並保留附件證據。
3. 加 `--rerank`：結果數量可以小於 `limit`；只保留有合法證據 Chunk ID 的相關郵件。
4. 原本 `python -m scripts.hybrid_search` 行為沒有改動。
5. Gemini Rerank 不直接回答使用者問題，這版仍不是 LINE Agent。LINE 問答整合保留給 v0.5.3。
6. 實際效果需要用標註的相關/不相關問題評估；LLM 也可能把不相關郵件誤判為相關，不能把它當作完美的真值判定器。
7. 新郵件仍須另外批次補建向量；本版不會在 Webhook 裡做 Embedding。
8. 仍使用 v0.5.2 的候選截斷範圍；向量端最多候選 2000 個較新 Chunk，資料量擴大後還需改進索引與查詢策略。

### 回復方式

如有問題，請先將 MCP 的兩個開關都設為 `false`，改用舊的 `hybrid_search`。如需回復程式，停止 Uvicorn 後，使用 `app.backup.before-v0521` 和 `scripts.backup.before-v0521` 備份復原；由於本版沒有資料庫 migration，不需要復原 SQLite（也不該直接覆蓋持續收到新郵件的正式資料庫）。
