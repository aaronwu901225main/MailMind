# MailMind v0.5.4.1 General Event Segmentation

> 本更新包是從 **v0.5.4** 直接升級的「重新設計版 v0.5.4.1」，**不是**先前的 `Extraction-Fix.zip`。先前那包不需要安裝。

## 設計重點

- 同封 Email 可有多個獨立 transaction / deadline 事件；不能將 Email 當成一筆交易。
- 依來源 `(source_type, source_id)` 合併有重疊的 Knowledge Chunks，找出每筆金額所屬的局部日期／時間／商家。
- 附件與郵件本文分別作為證據來源；不拿 summary、收到日期或模型臆測補齊交易日期。
- 時間與授權來源狀態保留在 JSON payload 中；**不新增資料庫欄位或向量索引**。
- `purchase` 統計代表「已辨識的消費通知」，會含舊版分類為 `authorization` 的紀錄。不是最終銀行請款。退款、取消另計，幣別不混算。
- 只有 `verified` 才能計入統計；同封 Email 多筆同額交易仍保留為多個 occurrence。
- 可選 Gemini fallback 仍受原本的雙重同意控制，**本更新不會開啟雲端擷取**。

## 1. 在 HPC 上備份

更新應在 `~/MailMind`，並先停止 MailMind Uvicorn；若 `mailmind-agent` 正在處理問題，先等工作完成或暫停 Worker。不要刪除舊資料。


## 2. 安裝與測試

將 `MailMind-v0.5.4.1-General-Events-patch.zip` 上傳至 `~/MailMind` 後：

```bash
unzip -o MailMind-v0.5.4.1-General-Events-patch.zip -d .
python -m compileall -q app scripts
python -m pytest -q
python -m scripts.check_setup
python -m scripts.check_events
```

本更新包附的事件子系統測試（原 17 + 新 11）在還原環境中已通過；**完整專案測試與實際 Gmail 格式驗收仍需在你的 HPC 執行**。

更新後重啟 MailMind Uvicorn，執行：

```bash
curl -s http://127.0.0.1:8000/health
```

應回傳 `version: "0.5.4.1"`。原本 LINE、MCP、FTS 與 Embedding 資料不需要重建。

## 3. 找到 11/19 彙整通知的 Email ID

```bash
python -m scripts.find_event_emails \
  --account-id "你的ACCOUNT_ID" \
  --subject-contains "消費彙整通知"
```

結果會印出 `Email ID` 與該封信可用的 `body/attachment` Chunks 數量。這是帳號範圍內的唯讀查詢；若 `chunks=0`，代表沒有可供可靠擷取的原始文字，需要另外重新取得該封郵件，而不是讀摘要猜數字。

## 4. 先預覽，不修改事件資料

把下列 `EMAIL_ID` 換成上一步結果：

```bash
python -m scripts.reprocess_event_emails \
  --account-id "你的ACCOUNT_ID" \
  --email-id "EMAIL_ID" \
  --preview
```

**只要原始郵件文字保留了三筆日期與金額，理想情況是**：

```text
transaction 2026-11-19 TWD 8300 ... verified
transaction 2026-11-19 TWD 20000 None verified
transaction 2026-11-19 TWD 26400 None verified
```

數值 `8300/20000/26400` 是以新臺幣分儲存，分別是 NT$83、200、264，合計 NT$547；商家沒有出現在原文時應為 `None`。如果 Preview 只有一筆、出現不合理金額或未讀到三個日期，**先不要正式重處理**。這可能代表 Gmail 轉成純文字時表格欄位流失或來源 Chunks 截斷，不能靠 Regex 自動猜測缺失資訊。

## 5. 正式重處理指定郵件

```bash
python -m scripts.reprocess_event_emails \
  --account-id "你的ACCOUNT_ID" \
  --email-id "EMAIL_ID"
```

這會以新的版本針對**指定的那封郵件**重新擷取，原子地取代該封舊 `structured_events`；其他郵件、郵件原文、摘要、索引與向量都不變。舊事件 ID 會改變。請在備份後再執行。

檢查該封信的逐筆結果與小計：

```bash
python -m scripts.inspect_event_email \
  --account-id "你的ACCOUNT_ID" \
  --email-id "EMAIL_ID"
```

預期是 3 筆 verified 消費通知、TWD 547.00（僅此封信）。如果用 `scripts.query_events --action aggregate --start-date 2026-11-19 --end-date 2026-11-20` 查詢，則會統計這個帳號 **所有** 11/19 的已驗證消費事件，可能不只這封信的 NT$547。

## 6. 後續擴大回填

在檢查單封與部分其他格式的準確率後，才考慮使用原本的批次指令：

```bash
python -m scripts.extract_events --account-id "你的ACCOUNT_ID" --max-emails 20 --mode local
```

因為 `EXTRACTOR_VERSION` 已升級到 `v0.5.4.1-2`，同一封信在新版本首次擷取時會重建；同來源／同版本的重複執行會跳過。這一步會改寫當批郵件的事件資料，先保留備份並以小批次測試。

## 限制與安全性

1. 現在的切分是結構感知的通用規則，**不是**任意 HTML／PDF 版型的通用解析保證。若 `getPlainBody()` 攤平複雜表格而丟失欄位配對，仍會需要 HTML 表格保留或其他抽取策略。
2. 來源文字被 v0.5.1 索引上限截斷時，事件擷取無法找回被截斷部分。
3. 一封郵件的重複消費會按不同來源位置保留；但**跨郵件的授權／請款通知對帳與交易去重尚未完成**，可能有重複通知，消費統計不是完整的銀行帳單。
4. 新事件只有來源中的日期、金額可對應、且沒有衝突才會 verified；無法可靠判斷者應為 review。這不能取代人工核對。
5. Preview 與 inspect 會在終端機顯示私人交易資料，分享 log 前請遮蔽姓名、卡號、識別碼及商家資訊。
6. LINE Agent 仍使用 v0.5.3 的 RAG 問答，**尚未新增自動使用 Analytics MCP Tools 的 Router**；本更新只改善資料引擎。
